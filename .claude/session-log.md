### Gotchas

- **Steps 4, 5 and 6 EACH found a defect the 2025 corpus could not have shown** — D1's unguarded past year, the stale second implementation of D1, and D10's multi-line lists. The corpus had zero explicit years, zero multi-line messages, and no occasion to collide with a closed month, so none was findable by any test written against it.
- **`batch-auto` warns on a duplicate and appends it anyway** — and because the row classified at 95% it was AUTO-appended, so it never reached the review page. The one place a human would catch it is the one place it does not appear. Caught by reading the log after the run.
- **A repeated id is NOT proof of a double-count.** `GenerateID` hashes `item|date|value`, so two genuinely separate identical purchases collide by construction; the log carries 8 such pairs legitimately.
- **The float tells you who divided.** `485/3` stores `161.66666666666666` and `3890/6` stores `648.3333333333334` — repeating decimals that prove the expander divided rather than a human typing. But `300/2` is exactly `150.0`, so that case was only settled by reading the original Telegram messages.
- **`--dry-run` on `batch-auto` skips the WORKBOOK, not the log append** — do not reach for it as a safe probe mid-close.
- `close-cycle.sh prepare` takes ONE csv and ONE year, but `batch-auto --year` / `apply --year` are only the ladder's FALLBACK for a bare `DD/MM`. Only `generate-workbook --year` really selects rows, which is what made one review pass over five months legitimate.
