## Active Decisions

### Identity — locked (session 67)
- **Identity is DERIVED, never trusted.** Any function that rewrites a value must rewrite whatever was computed from it. `apply`'s `entriesWithCanonicalDates` rewrote each entry's date and kept its `ID` — a hash of that date — so apply looked up an id it would never itself write. The miss is SILENT (unfound → treated as new → appended), so the symptom is a duplicate expense, not an error. Third appearance of this shape after T-35 and T-18; treat a value and its derived key as one edit, always.
- **The one deliberate exception is RETIRED — the logs were migrated (s74).** Both live logs are now fully self-consistent: every `id` equals `GenerateID` of its own row, and every date is `DD/MM/YYYY` (measured after migration: **2159/2159** expense rows, **717/717** classification rows). The rule "identity is DERIVED, never trusted" now holds everywhere on the live path, with no exception to remember.
  **What the s70 record got right, and the distinction it missed.** It said "recomputing drops the joins to zero", and that is true of a **one-sided** recompute — rewriting the expense log's ids from its new full dates while `classifications.jsonl` still stored `DD/MM`. It is NOT true of a **two-sided** migration: read each classification row's year off the join FIRST, rewrite its date, then recompute ids on both sides from the same full-date strings. Measured: **403 shared ids before, 403 after, and all 717 pairings identical** — not just the count, the actual pairings. The two-sided option was never costed in s70.
  **Why it was safe to do, all verified before writing:** every one of the 649 year-less classification rows resolved by join (0 unresolved, 0 inferred — the `timestamp` is useless for this, all 649 say 2026 because the backfill bulk-wrote them); all five workbooks 2022–2026 came out **byte-identical**, on a check first proven to move when a value changes and not when an id changes; and the migrator refuses to write anything on an unresolved OR an ambiguous row (both guards mutation-verified). Tool: `.claude/scratch/migrate_ids.py`; backup `backups/id-migration-20260831-181133/`.
  **The trap that nearly shipped, and the guard that now catches it.** 38 expense ids each carried TWO dates differing only by year (`20/12/2023` and `20/12/2024`) — inevitable, since the id hashed a year-less date. A `{id: date}` dict silently keeps the last, so those rows would have been assigned a coin-flip year. The pairing check did NOT catch it: before and after used the same wrong lookup, so it passed. It was found by asking whether the lookup was ambiguous, not by any check that existed. **Zero classification rows referenced those ids, so nothing was harmed** — and the migrator now hard-fails on ambiguity rather than choosing.
  **Consistent is NOT unique, and this is the live constraint on T-65.** Collisions fell 46 → **8**; the 8 that remain are genuine same-day duplicate purchases (`Acupuntura 04/10/2025 90,00` ×2) which correctly hash alike. So **an id can name two rows**, and an id-keyed supersede record cannot say which one it supersedes. T-65 needs an occurrence discriminator or an explicit "supersedes every row with this id" semantic. Its older constraint — "key off the STORED id, never recompute" — is now MOOT: recomputing gives the same answer.
  **Two things this does not cover.** The per-year legacy logs (`expenses_log-{2022,2023,2024,allyears}.jsonl`) were deliberately NOT migrated — superseded historical artifacts. And `close-cycle.sh restore` on a run dir predating s74 would copy PRE-migration logs back over the live ones and silently undo all of this.
- **A guard is not a guard until it has been broken.** Session 67 hit four instances of a check reporting success while testing nothing: a cached acceptance pass, a generated test comparing the parser to a second call to itself, the silent id miss above, and a fixture sweep that blinded its own end-to-end test. Mutation — break the guarded thing, confirm red — is the only cheap discriminator, and its result belongs in the commit message.
- **A mutation that fails to COMPILE proves nothing (s72).** Deleting a field to test a seam made the package unbuildable: red came from the compiler, not the test, so the guard was never exercised. The valid mutation changed the SOURCE COLUMN instead — it still compiled, and then discriminated precisely, failing only the seam test while the consumer package stayed green. A mutation must leave the program runnable or it measures nothing.
- **Assert BOTH directions, because a broken check fails identically to a working one (s70).** A new assertion's three mutation cases all went red and all looked like caught regressions; the check was simply broken (its jq indexed the wrong object) and would have aborted every real run. When failure calls `die()`, red proves nothing on its own — only a case that MUST PASS discriminates.
- **A deliberately-wrong fixture needs its reason where the reader stands.** `apply-stale-id` carries an id hashed from the pre-canonical date on purpose, and is the only fixture that can catch an id regression. That caveat is recorded in the fixture README, the package memory AND the index, because otherwise the next reader "corrects" it.

### Measure before building — locked (session 72)
- **The cheapest way to size a feature is often a join over data you already have.** A1 and B1 were both scoped from `.claude/scratch/close-20260818-120248/`, written by the previous session — no new run, no model, ~10 minutes. It produced a GO for A1 with a precision number, and it KILLED B1 outright by delivering, for free, the one measurement B1 existed to obtain. **Ask what the existing artifacts already answer before building the thing that would answer it.**
- **A dropped feature is a result, not a failure.** B1 (gate-to-review) was the approved plan. The measurement showed its premise was false — the 17 auto-inserted rows were never unseen, because `close-cycle.sh:220` feeds `review` the FULL `classified.csv` — so it was dropped and T-65 promoted in its place. Re-check a plan's PREMISE when new data lands, not just its execution.
- **A small unexplained discrepancy is a defect, not rounding.** The first gate-precision join reported 26 corrections against a known total of 25. That single-row overshoot was the only visible symptom of duplicate item names (`San michel` ×3) collapsing in an item-keyed dict; had they fallen the other way the arithmetic would have reconciled and a wrong number would have shipped looking right. **Carry a checksum that can FAIL**, and treat a near-miss as the tell it is. The fix was a POSITIONAL join, verified on item AND date across all 65 pairs before use.
- **A correction goes where the reader stands, not only in the new report.** `t42-close-findings.md`'s "without any human seeing them" was false and load-bearing for WS-D, so the correction was inserted INSIDE the `ref:auto-insert-unrepairable` block that readers resolve at runtime — not left to a newer file they might not open.
- **Documentation that nothing checks will be wrong and nobody will know.** `test/README.md`'s column table had been missing `type` since RUI-4 in session 33 — ~39 sessions — and nothing broke, because it is prose. The contract is the seam test. When correcting such a table, say which artifact is actually authoritative.

### An advisory signal must not become an authority — locked (session 72, A1)
- **71.4% is worth SHOWING and not worth APPLYING.** The keyword hint recovers 10 of 25 corrections, but auto-preferring it would inject errors on roughly 3 of every 14 rows it fires on. A signal good enough to inform a human is frequently not good enough to act unattended, and the two thresholds are different decisions. The page renders it beside the model's answer in the "needs attention" colour, never the colour reserved for a confirmed choice.
- **A predicate that consults the answer it predicts is not a predicate.** A generated draft compared the keyword to the REVIEWER's final choice rather than to the MODEL's prediction. It would have produced plausible numbers from something that cannot run at review time at all. Same circularity family as a test comparing a parser to a second call to itself.
- **The hint stops at the human.** It is deliberately NOT carried back through `exportReviewed()`: it is input TO the decision, not part of it, and a value crossing that unguarded JS hop would be a second T-61.
- **Ship the reachable setting, not the general one.** Strict specificity 1.00 only — not because a middle setting is structurally impossible (`MatchStrength` can return unambiguous-at-0.8) but because `review` loads no keyword index and has no consumer for the extra signal. A configurable threshold here would be a knob with nothing behind it. (Measured: every row scoring in [0.70, 1.00) this month was ambiguous, so the looser threshold was inert.)
- **Append new columns; never insert.** `expect.NoneWereAutoInserted` and `OutputFileHasColumns` read positionally, so an inserted column silently retargets them rather than failing to compile.

### The fast test group is blind to format changes — locked (session 72)
- **`-short` green does not mean the contract holds.** Widening the classified-CSV contract passed the deterministic group AND the whole unit suite, then failed six `-full` scenarios. Every assertion about `classified.csv`'s SHAPE sits behind `extern.RequireOllama`, because producing a real one means classifying. T-39 split the suite so the fast path runs after every edit — which makes a format change invisible exactly while it is being made. **Any change to the classified/review CSV shape runs `-full` before it is called done.** Check `/api/ps` first and unload a foreign resident model (`POST /api/generate` with `"prompt":"", "keep_alive":0`); 8 GB of someone else's model on a 12 GB card is what turned a ~110s run into a 3602s timeout in s64.

### Date/year policy — locked (sessions 65, 67)
- **`date_year` is a per-close-cycle switch, not a permanent setting.** Chosen over deleting it and relying on rung 4: the two agree on every past-dated bare input but diverge on a bare date **later in the year**, where rung 4 is wrong for a close.
- **Its staleness must be visible, not silent.** Warn only when BOTH hold: the config rung actually supplied this expense's year AND that year is below the current one. This is *why* `parse` reports `YearSource` — re-deriving the ladder in `cmd` would be a second copy free to drift.
- **The batch form of that warning is ONE line per RUN carrying a count (T-49, s67).** Per-row would print an identical line for every bare-dated row (300 for a 300-row statement) and train the reader to ignore stderr; hoisting above the loop would fire even when every row carries an explicit year. `--resume`-skipped rows are counted deliberately — a stale year gives them wrong predicted ids, so resume silently matches nothing, which is the case the warning most needs to cover.
- **Future-dated ENTRY is refused (T-47, provisional), and `apply` inherits it (s67).** Year-scale, not day-scale. In `apply` a future-dated reviewed row downgrades to `failed` with a non-zero exit rather than being written — loud rather than silent, which is the rule's purpose. Per-row failure honesty preserved. **Past-side bound deliberately NOT added (T-48).**
- **An enum's zero value must not name a real member.** `YearSourceUnknown` sits at zero so a failed parse cannot report a plausible rung to code that reads the field to decide.
- **A year-less date is kept for EVERY target year, and that is a data-model constraint, not a bug (s70).** `scanEntries` keeps an entry iff `entryYear==0 || targetYear==0 || entryYear==targetYear` — deliberate, so the legacy per-year logs still work with `--year N`. The consequence is that a year-less canonical log leaks wholesale into any other year, **at exit 0**: `--year 2026` against the old log produced a 107K workbook holding all 733 of 2025's expenses relabelled 2026. This is why the merged, year-explicit log had to become canonical before the first 2026 close, and why a rollover is verified with a check that can FAIL (compare sizes across years) rather than by reading a success message. **T-65 inherits this directly:** a supersede record with no date, or a year-0 one, would leak into every year by the same mechanism.

### Parse boundary — COMPLETE (session 67)
- **Two doors, one ladder.** `Fields(item, dateStr, valueStr, opts)` for a caller holding three strings; `Date(dateStr, opts)` for one whose other fields are already typed (`apply` reads `reviewed.json`, where the JSON decoder typed item and value). `Fields` DELEGATES to `Date` — the two year validations are what stand between a mistyped year and a row that hashes cleanly into both logs and then vanishes from the workbook, so they must not exist twice.
- **The classified CSVs carry the CANONICAL date.** `review.ReadQueue` hashes that column into `reviewed.json`'s id while both JSONL logs hash canonical; emitting the raw form handed the review queue an id `apply` would never write.
- **The CSV `value` column keeps the RAW token, never the parsed float.** It is the only place an installment count survives into the review queue; writing the float erases it silently.
- **The 3-field CSV split stays in `cmd`** (plan §11 D1) — a different input FORMAT from the 4-field semicolon form, not a drifted copy; merging them would break error locality.

### Test architecture — locked (session 64)
- **`Scenario.Given` must NOT become a slice.** Every scenario names exactly one Given; the name IS the documentation. Compose INSIDE helper definitions with `harness.Events(...)`.
- **The engine owns scenario plumbing (harness v1.1).** No Given sets `ctx.BinaryPath` or `ctx.FixtureDir`. Engine changes stay ADDITIVE.
- **An empty Given body means the scenario has no precondition** → omit `Given:`.
- **Given and When name opposite things.** Given: arguments are plumbing → implicit. When: arguments are the SUBJECT → explicit.
- **Composed setup accumulates and flushes once** — `ctx.State` + `ctx.BeforeWhen`.
- **A Given must NOT run the binary inline (s69).** `SetupBinaryConfig` accumulates keys and flushes `config.json` from its own `BeforeWhen`, so during the Given phase the binary has no config to read. A Given that needs a prior CLI step registers it as its own `BeforeWhen`; hooks fire in registration order, so the canonical Given's config flush lands first.
- **Tests build parsed values via the real parser, never struct literals** — `YearSource` is recorded by `resolveDate`, so a hand-set field tests the literal rather than the ladder.
- **A seam test beats two half-tests (s72 restates T-54).** The writer's own test proves a column is emitted; the reader's own test proves it is read; each was verified against its own idea of the format, which is how T-54 shipped. Feed the REAL producer's bytes to the REAL consumer. Measured: reading the hint from the wrong column failed ONLY the seam test while the consumer package stayed green.

### Close cycle — one vocabulary, one source (session 68)
- **The taxonomy has exactly one home: `config/taxonomy.json`.** `review` used to derive its picker from the workbook's Referência sheet, giving the close cycle two vocabularies that drifted 7 leaves apart. The human picked from one set and `generate-workbook` routed with the other, so a divergent pick was warn-skipped and the expense vanished with no error. Worse, the mismatch inverted the feedback loop: two picks were logged as CORRECTIONS — the highest-priority few-shot source — teaching the classifier a spelling that cannot route. **A second source of truth for the same vocabulary is not redundancy; it is a silent data-loss mechanism.**
- **`BuildTaxonomy` must never sort.** The old sort existed only because it folded workbook rows through Go maps, whose iteration order is random. A JSON array carries the author's order, so sorting would silently reorder the user's own picker.
- **A documented producer output is tolerated; corruption is not.** `ReadQueue` skips a row with empty date/value (the shape batch-auto deliberately writes for an unparsed line) and hard-errors on a bad number, bad confidence or wrong field count. Widening the tolerance to "skip anything unparseable" would turn a corrupt file into a quietly short queue.
- **Skipping without reporting is not a fix.** Dropping the unreviewable rows silently would trade a loud failure for a lost expense. The warning is mandatory, lives in `cmd` (not the library — same reason `parse` reports `YearSource` instead of printing), and is per-row here because it fires once per PROBLEM, unlike T-49's per-good-row warning that had to collapse to a count.
- **A convenience that removes an expressible request is a capability loss.** `generate-workbook --taxonomy` now falls back to config, but `--entries` deliberately does NOT: omitting it is how you ask for an empty year skeleton, which year rollover (T-03) depends on.
- **A fixture that TRANSFORMS producer output is asserting a contract neither side implements.** It is not bridging a harness limitation — a legitimate fold point is a step that genuinely cannot run here (a browser, a human). Reformatting is not one. Feed the real producer's bytes to the real consumer instead, and no fixture has to be kept in step.

### Cross-boundary counts — locked (session 69)
- **A field whose absence is indistinguishable from a valid value must be REQUIRED, never defaulted.** `reviewed.json`'s `installments` decodes to 0 when the key is missing, so defaulting to 1 would silently accept a producer that stopped emitting it — the T-54 shape, where a reader tolerated a spelling nothing wrote. `validateEntries` rejects `< 1` and names the entry, so a broken export fails LOUDLY at the next hop instead of under-recording every installment purchase forever.
- **A count and the label describing it are ONE edit.** `printSummary` prints "Appended: N rows" and was truthful only while entries and rows were 1:1; threading installments broke that identity without touching the label, so a `900,00/3` purchase printed "1 rows" and wrote 3. `rowsWrittenFor` mirrors `expandEntries`' own `<=1` rule — a summary derived from a different rule than the writer will eventually disagree with it.
- **When two components share an implementation, an equality test between them proves nothing.** Comparing apply's written ids to `appender.PredictEntryIDs` is circular: both call `expandEntries`. The honest claim spans two INDEPENDENT derivations — apply takes a typed JSON float, `batch-auto --resume` derives the same value from a raw `100,00/3` token through `internal/parse` — and is expressed as a behavior (`--resume` recognises the series) rather than an identity.
- **The `exportReviewed()` JS hop is UNGUARDED, and that is recorded rather than papered over.** Deleting `installments` from the export leaves the entire Go suite green — measured by mutation, not assumed. No Go test can execute browser JS, and a committed browser test needs a Node or `playwright-go` toolchain in a Go-only repo. **Do NOT close it with a hand-authored fixture**: a `reviewed.json` written to contain the field asserts a contract the producer may not implement, which is exactly how `review` could not read real `batch-auto` output for months.

### Repairing rejected input — locked (session 71)
- **A rejection reason is METADATA, so it belongs in a comment, not a field.** The retired `batch` writer appended it as a 4th semicolon field; `parse3FieldLine` splits with `SplitN(line, ";", 3)`, so the reason landed inside the VALUE and the file never re-imported even after the data was fixed. Written as a trailing `#` comment the same file is repaired in place and re-run as-is. The general rule: when a tool emits something for a human to edit and hand back, the annotation must sit where the parser already ignores it.
- **Do not widen a parser to accept its own annotation.** The alternative considered was to ignore surplus semicolons. That would let the 4-field `add`/`correct` form (`item;date;value;subcategory`) through `batch-auto` with the subcategory silently discarded — the T-54/S2 silent-acceptance shape. `stripTrailingComment` therefore requires the `#` to be whitespace-preceded AND the three fields already complete, which keeps `Mesa #5` as data and keeps a real 4-field line failing loudly.
- **An artifact whose EXISTENCE is the signal must not be written empty.** `failed.csv` is absent when nothing was rejected, and `close-cycle.sh` asserts it exists exactly when the reject count is non-zero. An always-written empty file would report a problem that did not happen; a never-written one hides rows that reach no other durable artifact.
- **A check must run BEFORE the step that can abort.** The new reject assertion was ordered after `review`, which exits non-zero when EVERY row was rejected (T-69) — so it was skipped in precisely the case it existed for. Found by smoke-testing the script against an all-malformed batch, not by reasoning about it. Order an assertion by what it READS, not by where it reads well.
- **Metadata regenerated each run must not be carried forward.** Re-running an unrepaired `failed.csv` appended a second copy of the reason every pass; the projection now writes the stripped line. Measured 106 → 204 → 204 chars, i.e. it converges. A row with fewer than 3 fields cannot have its comment stripped and absorbs one copy — documented rather than fixed by weakening the rule.

### Two notations for one concept — SHIPPED (session 73; decided s72, filed s71 as T-64)
- **`405,25 x4` MULTIPLIES.** Confirmed by the user in s72: the written number is the PER-INSTALLMENT amount, so `405,25 x4` totals 1.621,00 across 4 rows. This is the **inverse** of `total/N`, where `ParseCurrencyWithInstallments` treats the written number as the TOTAL and DIVIDES. Same digits, **4× apart**. Recorded in agent memory as well, because a wrong direction here is a silent 4× error in the workbook.
- **SHIPPED (session 73, PR #67).** Both token orders are accepted (`405,25 x4`, `646,25 4x`) plus the retail `4x405,25`, case-insensitively. Both notations are pinned in ONE test table, deliberately adjacent, so a reader who conflates them must edit two neighbouring lines that contradict each other.
- **Ambiguity is DETECTED, not resolved by fiat — and that is a different question than the obvious one.** A grammar answers "what does this mean?"; the shipped design asks "is there more than one thing this could mean?", which is what the hazard actually turns on. Three readings (`value x count`, `value count x`, `count x value`) are tried and the token resolves only when EXACTLY ONE holds; two holding is an ERROR. So `4x5` and `646,254x` are rejected rather than guessed. **The asymmetry is what justifies it:** rejecting costs one edit, because T-63 returns the row in `failed.csv` with its reason inline, while guessing writes a budget row wrong by the installment count and indistinguishable from a legitimate one. Reach for this shape whenever a cheap rejection path exists and a wrong answer would be silent.
- **Report shape-match separately from value-plausibility.** Collapsing them makes the specific objection unreachable: the first local-model attempt returned a generic format error for `405,25 x0` instead of "must be positive", because one boolean could not distinguish "not a value/count pair at all" from "a pair whose count is out of range". Keeping them apart also lets an implausible count disambiguate, so `4x100` resolves rather than becoming ambiguous.
- **This is not a synonym problem, and the ambiguity was expensive.** The notation was planned long before s71 but never written down, so s68 recorded it as a typo and both that report and a fixture README had to be corrected. Contrast the s68 S4 finding: `- 1/4` and a bare `4x` prefix are input ERRORS, not notations to learn. **Confirm a domain convention with the user rather than inferring it from data** — guessing reproduces the T-21 harm (a wrong installment count is indistinguishable from a legitimate entry) with a multiplier on top.

### "Retired" is a plan, not a property — locked (session 73)
- **Check the registration, not the label.** The T-64 commit message claimed `ParseCurrencyWithInstallments` had "two live callers". It has three: `models.NewExpense`, reached from plain `batch` — which is retired-but-not-deleted and still `rootCmd.AddCommand(batchCmd)` at `batch.go:44`. Adding coverage to a path WS-E will delete is waste — but the claim in the commit message was wrong, and a wrong claim about blast radius is worth a correcting commit.
- **The general form:** this is the same failure mode as T-54 and T-72, aimed at prose instead of code — something everyone believed that nothing enforced. When a doc asserts a component is dead, unreachable, or unused, verify it mechanically before relying on it.

### One parse site, or the divergence comes back — locked (session 73, T-72)
- **A function with two callers and a normalization step only one of them applies WILL diverge, and both sides' tests will stay green.** `review.ReadQueue` called `utils.ParseCurrencyWithInstallments` directly and so never stripped BR thousands, so `writeClassifiedCSV` could emit a `1.234,56` the reader hard-errored on — killing the entire review step over one row. Third appearance of the shape after T-54 and the s67 slice-4 id miss.
- **The fix is a door, not a patch.** `parse.Value` is the value-only entry point and the mirror of `parse.Date`; `Fields` DELEGATES to it so normalization has exactly ONE call site, which is grep-verifiable and therefore checkable by the next reader. Patching the symptom (teaching each caller separately) leaves the class of bug intact. Design **Q3** — "the boundary owns ALL input normalization" — is what decided placement, over the superficially safer option of pushing normalization down into `pkg/utils`.
- **A mutation can prove two things at once, and the second may be the more useful.** Deleting the normalization inside `parse.Value` turned exactly the thousands tests red while both multiplier tests stayed green. That proved `ReadQueue` routes through the boundary — AND that the multiplier test is BLIND to that routing, so the case that looks redundant is the only one carrying the guarantee. **Record which test is load-bearing where the deleter will look**, or a future tidy-up removes it.

### Running the close — locked (session 70)
- **A dry run that repeats the expensive human step is not insurance, it is a tax.** The scout's sandbox was right when the chain had never run; once the failure modes are known, append-only JSONL means a snapshot is a COMPLETE undo at ~1% of the machinery — whereas a full rehearsal costs the reviewer 45 hand-categorised rows that are then thrown away. Weigh a safety mechanism against what it costs the HUMAN, not only against what it protects.
- **A baseline must be taken at the point the measurement is about.** The close reconciles `appended rows == Σ installments`, and its two halves were originally measured against different points in time: the row delta spanned batch-auto AND apply while the dedup set predated batch-auto. It cancels out only while the reviewer confirms every auto-inserted row, and reports a phantom regression the moment one is SKIPPED. Hence two snapshots — `logs-before/` for restore, `logs-after-batch/` for reconciliation — which must never be collapsed into one.
- **The human-in-the-loop break stays, and the reason belongs in the script.** `exportReviewed()` is a browser Blob download with no headless path; synthesising `reviewed.json` to make the close one command would make the script a hand-authored stand-in for a producer it does not implement — the T-54 shape and the T-61 trap. The rationale lives in the script header because "make it one command" is the obvious future refactor.
- **A backup outside the `*.bak-<stamp>` convention is not gitignored.** Real financial data sat untracked under a `.pre-promote-<stamp>` name that matched no rule. The convention is load-bearing, not cosmetic.
